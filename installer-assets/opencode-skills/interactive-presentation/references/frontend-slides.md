# Native HTML authoring with frontend-slides

Use this route for straightforward new web decks; incumbent projects retain
their engine. The maintained owner is
[zarazhangrui/frontend-slides](https://github.com/zarazhangrui/frontend-slides).
TH provides context and delivery scope; upstream owns the authoring method.

## Acquire or reuse the owner resource

Reuse a readable, independently owned checkout when available. Otherwise, when
dependency preparation is authorized, clone the official repository into an
isolated external provider directory, such as `workspace/providers/frontend-slides`.
Inspect an existing checkout's origin and revision; preserve its changes.
Record the actual repository URL, resolved commit and resource path in the
workspace's research note. Do not assume that a historical research commit is
the current installed method or reset an independently owned checkout.

Read that checkout's `SKILL.md` and the resources its applicable route requires.
Follow its current context, style, authoring and rendered-assessment instructions;
load its references progressively rather than copying its catalog or viewport
CSS into TH. Direct instruction reads are usable when native registration is
absent, but do not establish host discovery or activation.

## Pass the meeting context and effects

Supply topic, audience, meeting objective, real content/assets, confirmed visual
direction, destination, supported browser capabilities and authorized endpoint.
Reuse settled context and identity; resolve material choices with the actual
content. Upstream defaults for editing, export, wheel handlers or deployment
apply only when they fit the requested effects and interaction context.

Keep the authored deck at the explicit target and source provenance/captures in
the workspace. Do not vendor the upstream skill or install every host runtime.
Its standalone HTML recipe does not justify replacing an existing application's
React/Vue components or presentation engine.

If acquisition, an applicable method or rendering is unavailable, state the
specific missing capability and supported recovery. Continue useful independent
work without claiming equivalent upstream execution. The workflow's meeting-size
checks still apply to content present in the delivered deck.
