
# UI design

Ground visual decisions in the actual product. The current general agent
coordinates this workflow with native tools and permissions; selecting it does
not activate a pipeline or replace Main with another coordinator.

## Establish the product and endpoint

Reuse the bound [context](../workspace/SKILL.md); Main retains useful returns there.
Read the product/design records, affected implementation,
components, tokens, assets and supplied references. Resolve the surface, users,
primary task, real content, constraints and requested endpoint from that context.

- **New UI:** derive hierarchy and direction from those users, tasks and content;
  a new feature inside an established product inherits its confirmed identity.
- **Refinement:** preserve established brand, stack, component conventions,
  behavior, factual copy and status meanings within the requested surface.
- **Redesign:** replace identity only when explicitly authorized; retain product
  truth, function, constraints and pinned brand commitments.
- **Audit:** evaluate actual roles/tasks and loading, empty, error, success and
  recovery states. Use relevant upstream critique/audit and existing
  [UI testing guidance](../../agents/testing-refs/_index.md), including keyboard/
  focus, responsive/browser/device and manual accessibility limits. Distinguish
  expert hypotheses from participant-observed usability. Keep findings in the
  caller's report; this analysis endpoint ends before redesign or product edits.

Resolve missing material scope or identity decisions before dependent work;
continue independent context preparation. Do not invent an example application
or infer redesign authority from a refinement request.

## Use the maintained visual workflow

Read [Impeccable preparation and invocation](references/impeccable.md). Reuse
the usable active-runtime capability and follow its actual installed compiled
instructions and matching playbooks. Pass the product context, target, objective,
authorized effects, constraints and audit, design-only or implementation endpoint.
Upstream owns visual methods and project design records; its advice grants no
additional authority. Disclose unavailable capabilities and use supported fallbacks.

An audit uses the applicable upstream analysis method and evidence/reporting
below, without entering direction selection or design/implementation steps.

## Resolve the visual direction

Read incumbent assets and supplied references before researching alternatives.
When identity or color direction is unsettled or its replacement is authorized,
perform bounded internet research relevant to the audience, content, use scene
or intended identity. Retain selected links, observations and adaptation reasons
in the workspace; adapt their useful qualities instead of copying an identity
or choosing a generic trending palette.

Compare meaningfully different treatments only to resolve a material open
direction, using the same actual representative product screen. New UI may use
a proposed screen grounded in the product's task and content. Settled-brand
refinement requires neither fresh research nor a palette comparison.
Let the installed workflow map direction to semantic roles and assess applicable
accessibility, interaction states, themes and platform conventions, preserving
incumbent components, stack and status meanings within authorization.

## Deliver and continue within scope

Use [design](../design/SKILL.md) for needed solution decisions under its
functional-first proposal contract; reconcile canonical OpenSpec intent when
present. Before frontend implementation, present or reuse an accurate structural
wireframe through [sketch](../sketch/SKILL.md). A visual comp does not silently
replace that preview or require a second proposal.

A design-only request ends with a visual result in declared real local artifact
storage or the explicit destination and unresolved decisions, before production
edits. Explicitly requested implementation or improvement continues through
authorized scoped changes, relevant project checks and upstream rendered
assessment after material decisions, without another blanket approval.

Link native visual artifacts from the context; unsupported upload stays pending.
Retain upstream finish evidence. Report actual
screens, states, themes, device classes and omissions. Check existing screenshots
or fixtures for target and freshness; label them as qualified evidence, not a
fresh render. If the app or a required capability cannot run, preserve supported
partial results and mark fresh rendered verification or missing finish checks
pending. Dependency readiness, source review and successful commands or repository
tests do not establish visual quality or measured improvement.
