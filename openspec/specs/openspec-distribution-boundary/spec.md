# openspec-distribution-boundary Specification

## Purpose
Defines how project-local OpenSpec integrations coexist with Team Harness packaging without being misrepresented or redistributed as TH-owned runtime assets.

## Requirements

### Requirement: OpenSpec-generated integrations retain external ownership
TH SHALL treat tool-native skills and commands generated by OpenSpec as OpenSpec-owned project artifacts. TH MUST NOT copy, rewrite, rename, or publish those artifacts as canonical Team Harness skills.

#### Scenario: OpenSpec generates runtime adapters in the TH source repository
- **WHEN** `openspec init` or `openspec update` creates supported skills or commands for installed runtimes
- **THEN** those files remain usable in the repository and retain their OpenSpec ownership and generation metadata

#### Scenario: OpenSpec updates generated adapters
- **WHEN** a supported OpenSpec update regenerates its runtime files
- **THEN** TH accepts those files as externally managed inputs and verifies that no TH-owned canonical skill or command was overwritten

### Requirement: Team Harness packages include only declared TH-owned roots
Every TH distribution path SHALL select artifacts from an explicit set of TH-owned package roots. Repository-local OpenSpec-generated files outside those roots MUST NOT appear in an installed Team Harness plugin or runtime bundle.

#### Scenario: A Team Harness runtime package is built
- **WHEN** the Go installer, Codex plugin, OpenCode bundle, Claude plugin, or another supported distribution is assembled
- **THEN** only declared TH-owned roots are packaged and OpenSpec-generated project adapters are absent from the result

#### Scenario: A generated OpenSpec file is committed to the source repository
- **WHEN** a release is built from a Git tree that contains committed OpenSpec runtime adapters
- **THEN** package assembly still excludes those files unless they are explicitly declared as an external dependency rather than a TH-owned skill

### Requirement: Distribution boundaries are verified across runtimes
TH SHALL have automated checks that enumerate shipped artifacts for every supported packaging path and fail when an undeclared project-local runtime file crosses the ownership boundary.

#### Scenario: Packaging tests inspect a clean fixture
- **WHEN** the fixture contains OpenSpec-generated adapters for Claude, Codex, and OpenCode
- **THEN** the tests prove that TH installation outputs contain only TH-owned skills and commands while the fixture's OpenSpec files remain untouched

#### Scenario: A packaging path accidentally sweeps the repository root
- **WHEN** a distribution change would include an OpenSpec-generated adapter outside the declared TH roots
- **THEN** the packaging test fails before release and identifies the unexpected artifact

### Requirement: Consumer repositories may retain OpenSpec integrations
TH SHALL NOT require ordinary consumer repositories to delete or ignore OpenSpec-generated runtime adapters merely because Team Harness is also installed. Packaging isolation MUST NOT remove or mutate consumer-owned OpenSpec files.

#### Scenario: TH is installed or updated in an OpenSpec-enabled repository
- **WHEN** the repository already contains OpenSpec-generated skills or commands
- **THEN** TH installs or updates only its own managed assets and preserves the OpenSpec integrations
