# Research an application

Answer the operator's development question about an existing application. The
current general agent coordinates the work and interprets the evidence; REA
supplies its maintained workflow and supported public analysis capabilities.

## Establish the scope

Resolve the application or artifact, research question, relevant journeys and
destination-project context from the conversation and existing evidence. If the
target is ambiguous, resolve it before analysis and continue independent context
preparation. An exploratory objective is valid without a destination project;
state assumptions rather than inventing project needs or choosing an example app.
Reuse the bound [context](../workspace/SKILL.md); keep file-tool storage separate.

Follow the upstream complete-source boundary: ordinary analysis of a complete
source repository uses normal repository research, without REA readiness or
provider commands. Preserve that route's actual source evidence and limits.
For artifact or runtime questions, let the upstream workflow select its applicable
method for any technology the installed dependency supports.

## Use the upstream workflow

Read [REA application research](../spec/references/upstream-tools.md#rea-application-research)
for selected-capability preparation, ownership and portable results. Resolve
`reverse-engineer-anything` instructions matching the actual package/server and
relevant guides, then follow actual MCP schemas or public CLI help. Reuse usable capabilities;
the CLI remains an option when MCP is unavailable, without changing host config.
Pass the question, target, journeys, project context, authorized effects and
workspace to the upstream workflow. Keep unavailable scope and version mismatches
visible; continue supported work and report concrete recovery for remaining gaps.

Main or a specifically scoped native executor owns application effects and
session lifecycle under native permissions. Follow the provider's passive observation
and active-scenario boundaries, application readiness and visible-result requirements.
Distinguish completed actions from verified visible outcomes and preserve external
session ownership. Existing research roles remain read/search; they return advisory
evidence and gain no implicit execution authority.

## Preserve evidence and interpret it

Keep complete original Evidence/artifacts under `research/rea/` in declared real
local operational storage. Retain identities, profiles, provenance, limitations,
omissions and diagnostics; verify the actual output destinations. Link summaries
and views to their original Evidence and use supported views for focused questions
instead of repeating completed analysis. Preserve a supported portable original
before closing a connection when later reuse needs it; retained IDs alone do not
survive a connection or become references for separate CLI calls.

Main retains interpretation in the same Page, or `research/00-research.md` in file
modes, linking portable original results. State scope, open questions, findings
and coverage limits. Separate observations, inferences and unknowns; static
relationships do not establish runtime behavior, and process success does not
establish exhaustive coverage.

For each material opportunity, explain user value, project fit or exploratory
assumptions, required adaptation and a concrete acceptance example. Link its
supporting Evidence or identify the inference. Findings remain advisory; Main
decides material follow-up and dispositions. Hand selected ideas and their evidence
to [design](../design/SKILL.md) or [spec](../spec/SKILL.md) within the existing scope;
research alone does not start implementation or activate a pipeline.
